# CourseMatch 团队规则增补（2026-09-28）

> 来源：项目负责人在 2026-09-28 转述并确认这是一份团队总结，见 [Issue #7](https://github.com/SilenVale/coursematch/issues/7)。本文件记录这次确认的**业务方向和边界**，不是逐名成员表决纪要，也不代表接口、数据库、代码或测试已经完成。历史 [需求基线 v1.0](./REQUIREMENTS_ANALYSIS.md) 保留原状；以下规则对其补选与身份等未展开处作增补，不改动轮次优先的主分配原则。

## D1 补选提交与结算

1. 主分配截止后为每位参与学生冻结的唯一 `lotteryNumber` 在所有补选轮次继续使用；它按学生绑定，不按提交时间生成，不得重抽。保存冻结快照、序号映射和生成规则版本，确保同一输入可重放同一结果。学生可查看本人序号；公开核验材料不得泄露姓名与其他人的完整志愿。
2. 仅已提交原志愿但未分配的学生可参与补选。每轮统一截止前，每人至多有一个当前有效的可接受题目；允许改选，服务端成功接受的最新有效版本参与结算。每次有效提交保留时间、题目、前一有效值和版本；非法或逾期请求不覆盖旧值。服务端时钟判定截止，恰好到点也拒绝。
3. 提交意愿**不占位**。学生可见题目实际剩余名额、当前有效补选意向人数及统计时间，均为汇总信息；意向人数不是已录取数，不展示他人身份或完整志愿。同题意向人数超过剩余名额时仍可提交；实际余量为零、题目未发布/已取消/不在本轮、资格不符或操作人无权时才拒绝并给出适当理由。
4. 到点后仅使用本轮最后一次有效意愿集中结算：同题按冻结序号升序取实际剩余名额，名额扣减和结果写入保持一致；未投或落选者保持未分配，不自动派入其他题目。输入快照、有效意愿、序号、规则版本、批次和输出须可复核。补选请求超时后先查当前有效版本，避免盲目重试造成误解。

## D2 空位与异常

1. 主分配批次不可变且只生成一次。新增补选轮次必须创建**新批次**，不能重跑、改写旧批次或重新抽签。
2. 补选结束后因退选、题目取消或资格纠错产生的空位先列为`待处理`，由有权限教师记录原因后选择`再开一轮`、`有依据的异常指定`或`关闭`；每次迁移保存操作人、时间、原因及受影响学生和名额。教师可查询待处理清单，学生可看到与本人有关的结果变化。
3. `有依据的异常指定`不是私下顺延：须属于预定义异常，校验学生资格、本人是否已有题目及题目容量，记录调整前后；不能把一般空位当作任意指定的理由。退选和名单/资格更正均须留痕。学生能否自助退选、允许的截止点、退选后再补选资格，以及资格纠错的优先处理办法，**本次未定**，须在实现前另行确认。
4. 活动进入`final`时，不得仍有未结算补选批次或无处置结论的待处理空位；`关闭`允许保留空位和未分配学生，但须记录决定，不得伪装成全部分配成功。此条是为状态机收敛提出的验收口径，仍需教师端负责人在设计评审确认。

## D3 名单、账号与授权

1. 教师维护参与名单；业务学号与系统 `userId` 分开，名单与账号建立唯一对应，名单增删改留痕。学生不能仅凭自报姓名或学号取得身份。服务端分别校验已认证、属于该活动名单、对目标资源有权；请求里的 `studentId` 不能替代会话主体授权。
2. 第一版**建议**由教师导入名单，再向本人安全发放单次使用、有限有效期的激活码/链接。激活码的交付、遗失补发与账号恢复方式尚待教师端和学生端负责人定稿；学校邮箱不等于身份认证。若采用密码登录，应配套登录限流与密码强度要求。

## D4 非功能验收口径

1. 原报告的 30 人/10 题、查询/提交各 20 次、2 秒/5 秒均只是**拟议冒烟基准**，不是已批准的正式性能验收，更不是实测成绩。先调查实际课堂规模和部署位置，再确定正式负载、并发度、p95 阈值、主分配耗时及样本量；300 人/100 题可作为候选压力场景，不能假装是真实班级人数。
2. 测试记录至少包含 GitHub commit、机器和服务端规格、数据库版本、网络位置、数据量、并发度、冷热缓存、每次耗时与失败数；同一主分配批次不能为凑样本重跑，应使用独立测试活动。
3. 3 人原型试用属于**探索性易用性检查**，记录任务完成、耗时、错误与原话，只能说明是否发现阻断性问题；不能据此宣称大样本易用性达标。量化验收若需要，另定任务完成率、时间/错误门槛或合适的问卷及样本量。

## 待定实施问题与验证

| 待定项 | 负责人/下一步 | 不得提前宣称 |
|---|---|
| 冻结任务在截止时如何触发、失败如何重试；序号生成与核验材料如何脱敏 | 教师端/测试负责人给出设计和失败用例 | 已可复现或冻结可靠 |
| 退选权限/截止/再补资格、资格纠错优先级、异常指定的具体审批与告知 | 教师端/学生端负责人确认 | 任何教师操作都可任意指定 |
| 激活码发放/补发、账号恢复及接口/错误码优先级 | 前后端与测试负责人共同设计 | 已有安全登录实现 |
| 真实规模、正式性能阈值/样本与运行环境；易用性是否另设验收目标 | 负责人、测试负责人，必要时咨询教师 | 2 秒/5 秒或 2/3 试用已达标 |

本增补的 D1/D2/D3/D4 先作为需求和设计依据；技术细节和待定项通过后续 Issue/PR 留痕。验收前仍须取得运行记录，不能以本文件代替实现和测试。
