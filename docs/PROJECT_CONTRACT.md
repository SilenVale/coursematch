# CourseMatch 项目任务契约

## 目标

完成一个可公开体验的学生选题系统，帮助课程教师更公开、公平地组织题目发布、学生选题与结果确认。

## 项目名称

- 课程官方选题：学生选题系统
- 产品工作名称：CourseMatch

## 第一版交付物

- 教师端题目发布和名额维护；
- 学生端题目浏览、筛选与志愿提交；
- 名额与重复申请校验；
- 教师端申请查看、确认或调整；
- 选题结果与进度公示；
- 登录、基础权限、数据管理、测试和公开部署；
- GitHub 仓库中可复核的课程过程证据（历史 Gitee/Wiki 记录通过证据索引定位）。

## 事实来源

- 《软件工程》实践课程教案；
- 《软件工程》项目报告撰写内容及规范化参考样本；
- GitHub 仓库中的团队基线；早期决策可参照历史 Gitee/Wiki 记录，但不能将文档自述等同于原始聊天确认。

## 约束与不做事项

- 小组最多 4 人，课程周期按 8 次课推进；
- 第一版以 Web 应用为目标，避免应用商店上架依赖；
- 不做支付、即时聊天、复杂社交、完整教务系统或未经验证的 AI 自动分配；
- 自主选题、题目规则和最终分配仍由教师决定，系统只提供透明流程与辅助建议；
- 任何真实学生数据仅在获得教师和使用者同意后录入测试环境。

## 验收证据

- 学生能完成一次从浏览题目到提交志愿、查看结果的完整流程；
- 教师能创建题目、设置名额并处理申请；
- 重复申请和超出名额能得到明确提示；
- 关键流程有测试用例、运行结果和用户体验反馈；
- 应用有公开访问方式，GitHub 保留项目过程与提交记录。

## 审批点

- 第一周：确认选题、成员、NABCD 与项目边界；
- 第三次课：与老师沟通选题确定和项目规划；
- 第二周结束前：冻结第一版需求与原型范围；
- 合并到 `master`：由仓库负责人或指定审查人确认。

## 待确认事项

- GitHub 协作者账号及权限（成员角色已记录在第一周立项材料中）；
- 实际使用场景是课程实践选题、毕业设计选题，还是二者兼容；
- 第一版技术栈、数据库和部署方式；
- 题目分配规则由教师指定的具体公平机制。
