# CourseMatch 模块评审问题单

> 先阅读 [团队共同基准](./TEAM_BASELINE.md)。每个人只回答自己的部分；目的是验证当前逻辑、发现真实问题、提出可落地的改进，不是重写项目规则。

## 怎样回答

每题用 3 至 6 句话回答即可，按下面格式写：

```text
结论：保留 / 建议修改 / 待团队讨论
原因：
建议做法（如有）：
它会影响的页面或数据（如有）：
```

如果提出功能创意，再补一句：**“用户在什么时刻用它，如何证明它有用？”**

## 汪奕辰：产品、原型与全流程

1. 从“教师创建活动”到“学生看到结果”，现有 Demo 是否让第一次使用的人看懂完整流程？哪一个页面或跳转最容易让人断掉？
2. 在填报中、已截止、分配完成、补选中四个阶段，学生和教师各自应该看到什么、不能操作什么？原型目前是否清楚？
3. 对学生来说，结果页至少要展示哪些信息，才能相信结果不是教师随意决定的？请按重要程度排序。
4. 教师端和学生端的页面信息是否有重复、缺失或互相矛盾？请指出具体页面和改法。
5. 你认为最值得加入 Demo 的一个“公平、公开、可解释”亮点是什么？它怎样在 30 秒演示中让人一眼看懂？

## 石俊贤：教师端、数据与分配逻辑

1. 教师在“开放活动”前必须填完哪些信息，系统才能确保后面可以公平分配？哪些字段缺失时必须阻止开放？
2. 活动开放后，教师还能修改哪些内容？题目、名额、资格条件、截止时间中，哪些一改就会影响公平，应该怎样处理？
3. 分配时如何保证“任何第一志愿都先于第二、第三志愿”，且同题同轮超额才使用随机序号？请用一个 5 人、2 个题目的例子检验现有逻辑。
4. 点击两次“执行分配”、题目临时取消、学生资格信息填错时，系统分别应该怎样处理，才能不出现超额、重复分配或无记录调整？
5. 教师端是否需要一个低成本但有价值的亮点？例如“开放前规则检查清单”或“分配完成后的过程摘要”。请选择一个，写清页面展示和必要数据。

## 刘家铭：学生端、志愿交互与结果解释

1. 学生浏览题目时，应该看到哪些公开信息，既能做选择，又不会泄露其他学生的个人志愿？
2. 学生添加、删除、调整第一到第三志愿时，哪些操作必须即时拦截或提示？请重点考虑重复题目、超过上限、空志愿和截止后编辑。
3. 当学生只填一个志愿、第二志愿已满、或不满足题目资格条件时，页面应分别怎样解释，才不会让人误以为系统出错？
4. 个人结果页怎样用一句话和一组数据解释“为什么我分到了 / 没分到这个题目”？请提出你认为最清楚的展示结构。
5. 学生端最值得做的一个体验亮点是什么？例如“志愿竞争风险提示”或“结果解释卡”。它不能替学生决定志愿，也不能泄露其他人的信息。

## 罗子超：测试、用户试测与验收

1. 请设计一组最小测试数据，能一次验证：第一志愿优先、同题同轮随机序号、题目名额上限、每人最多一个结果。写出预期分配结果。
2. 哪三个边界场景最可能造成“不公平”的争议？例如截止后修改、重复运行分配、人工调整。系统的正确表现应是什么？
3. 你如何验证结果解释不是空话？学生结果页至少应出现哪几项可复核信息？
4. 用户试测时，分别问一位“教师模拟用户”和一位“学生模拟用户”哪两个问题，才能得到可改进的真实反馈？
5. 你建议加哪一个能增强可信度的测试 / 演示机制？例如固定测试数据回放、分配前后名额对账、异常调整日志。说明它如何验收。

## 回收后怎样决策

负责人把所有答案分为三类：

1. **必须修正**：现有逻辑有矛盾、漏洞或用户会误解的地方；
2. **候选亮点**：能增强公平、公开、可解释，并且能在 Demo 中演示、能在课程周期内实现；
3. **暂不纳入**：实现成本高、无法测试、或会改变已冻结分配规则的想法。

最终只选择 1 个主亮点和至多 2 个辅助亮点，统一更新需求、原型、设计与测试材料。
