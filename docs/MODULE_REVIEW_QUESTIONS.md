# CourseMatch 模块评审问题单

> 先阅读 [团队共同基准](./TEAM_BASELINE.md)。每个人只回答自己的部分；目的是验证当前逻辑、发现真实问题、提出可落地的改进，不是重写项目规则。

## 怎样回答

每题用 3 至 6 句话回答即可，按下面格式写：

```text
结论：保留 / 建议修改 / 待团队讨论
原因：
建议做法（如有）：
它会影响的页面或数据（如有）：
```

如果提出功能创意，再补一句：**“用户在什么时刻用它，如何证明它有用？”**

## 汪奕辰：产品、原型与全流程

### 当前逻辑

- 产品以“教师配置 → 学生填报 → 系统分配 → 结果与补选”为唯一主流程；
- 原型需要覆盖填报中、已截止、分配完成、补选中四个状态；
- 学生结果必须能解释题目、志愿位次、随机序号和结果原因；
- HTML Demo 已可作为课程原型，低保真图和状态图用于补充说明。

### 请反馈

1. 这条主流程和现有页面是否已经足够让第一次使用的人看懂？哪一步最需要调整或补充？
2. 四个活动状态下，教师端与学生端的可见内容、可操作内容是否合理？请指出具体页面。
3. 在不增加复杂功能的前提下，你建议加入哪个最能展示“公平、公开、可解释”的原型亮点？

## 石俊贤：教师端、数据与分配逻辑

### 当前逻辑

**活动配置**：教师创建活动时填写参与学生名单、题目、每题名额、资格条件、截止时间和最大志愿数；缺少这些影响分配的信息时不能开放。

**开放期间**：学生可提交志愿；教师可查看汇总进度。题目、名额、资格条件和截止时间等公平性字段不允许直接修改。

**截止与分配**：系统冻结名单、题目、名额、资格条件、志愿和随机序号；先处理全部第一志愿，再处理未分配者的下一志愿；同题同轮超额才按随机序号决定；主分配只能执行一次。

**结果与异常**：教师查看题目名额使用和结果；仅对退选、题目取消、资格信息错误等异常调整，并记录原因、时间和名额影响。

### 请反馈

1. 上述四类逻辑是否完整、有没有矛盾或容易造成不公平的地方？请指出具体一项并给出修改建议。
2. 教师端哪些信息或操作最容易让老师误用？页面应怎样限制、提示或留痕？
3. 你认为教师端最值得增加的一个创新点是什么？请说明它在什么页面出现、需要什么数据、为什么值得做。

## 刘家铭：学生端、志愿交互与结果解释

### 当前逻辑

**浏览题目**：学生可看题目说明、资格条件、计划名额和汇总热度，但不能看其他学生的具体志愿或个人信息。

**填报志愿**：学生可填写 1 至 3 个不重复的有序志愿，截止前可修改，最后一次有效提交为准；截止后页面变为只读。

**查看结果**：分配后，学生看到最终题目、命中的志愿位次、随机序号以及每轮的成功或失败原因；全部志愿失败者进入补选，只能选择有剩余名额的题目。

### 请反馈

1. 这些学生操作是否清楚、有没有容易误解或遗漏的情况？请举一个具体页面或交互例子。
2. 志愿编辑和结果解释页面应怎样提示，才能让学生理解规则而不是觉得“系统黑箱”？
3. 你认为学生端最值得增加的一个体验亮点是什么？请说明用户何时使用、页面怎样展示、不能泄露什么信息。

## 罗子超：测试、用户试测与验收

### 当前逻辑

测试必须验证：第一志愿优先、同题同轮随机序号、题目不超名额、每人最多一个结果、截止后不能修改、主分配不能重复运行、补选只使用剩余名额、异常调整必须留痕。

用户试测则分别让教师和学生走完整流程，记录他们是否理解规则、是否知道下一步操作、是否相信结果解释。

### 请反馈

1. 上述测试范围是否漏掉了最容易影响公平或可解释性的场景？请给出一个要补充的用例。
2. 你认为怎样的测试数据和结果展示，最能让老师一眼确认分配算法正确？
3. 你建议加入哪一个低成本的测试、试测或结果复核机制，能提升项目可信度？请说明如何验收。

## 回收后怎样决策

负责人把所有答案分为三类：

1. **必须修正**：现有逻辑有矛盾、漏洞或用户会误解的地方；
2. **候选亮点**：能增强公平、公开、可解释，并且能在 Demo 中演示、能在课程周期内实现；
3. **暂不纳入**：实现成本高、无法测试、或会改变已冻结分配规则的想法。

最终只选择 1 个主亮点和至多 2 个辅助亮点，统一更新需求、原型、设计与测试材料。
