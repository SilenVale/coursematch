# CourseMatch 需求方案补充确认（2026-09-28）

> 项目负责人在第三次需求分析材料准备时确认以下方案，补充 [团队规则增补](./TEAM_DECISIONS_2026-09-28.md)。此记录不是逐名成员表决或教师批准，不追改此前报告的来源状态；实现与测试须另留证据。

## 已确认的需求口径

1. 补选最多 3 轮。没有统一的最短轮次时长，也没有单题独立作答计时；每轮开放前公布严格晚于开放时刻的服务端截止。未另选时长时默认开放 24 小时，截止不因暂时无人提交而提前；全轮无人提交则到点结算空意愿批次，不自动分题，剩余空位默认保持待处理、活动不能自动进入 `final`。若开放前设了其他正时长，以公布的截止为准。第三轮之后不再新开补选批次。
2. 单题 `capacity` 为 1～本活动当前有效参与名单人数；开放与冻结时均须重验，名单变化不能绕过上界。每题可容纳多人，每人最终最多一题。
3. 正式版以 HTTPS Web 服务及服务端数据库为目标；名单由教师确认，学生用一次性、限期激活码与本人账号唯一绑定。学校邮箱仅作经核实的联系渠道或可选提醒，不凭邮箱地址取得资格。
4. 教师端支持桌面 Chrome、Edge 的当前及前一主版本；学生端另支持当前版移动 Chrome、Safari。具体版本号须在测试时记录。主分配结果和新补选轮须在学生个人页显示状态、发布时间、截止和本人入口；邮件仅可选，短信不在首版范围。
5. 性能分两层：30 人/10 题只作冒烟，查询与提交的有效请求各至少 100 次、各自 p95 ≤2 秒、独立活动主分配 ≤5 秒，仍只报告观测值；正式压力测试目标为 300 人/100 题、30 人并发，查询与提交的有效请求各至少 100 次、各自 p95 ≤2 秒、失败数为 0，独立测试活动主分配 ≤5 秒。测试记录 GitHub SHA、服务端/数据库/机器/网络、数据量、缓存、逐次耗时与失败数；不得重跑同一主批次凑样本。数字是确认的**测试目标**，不是已取得的结果或真实班级规模。
6. 3 人试用仅作探索，记录完成、耗时、错误和卡点；如果后续能招募到 10 名未参与设计的学生，再以至少 9/10 独立完成核心任务、0 阻断性错误作为量化候选线。能否招募 10 人及执行时间目前未定。

## 仍需设计、征询或实测

- `final` 前所有未结算批次和待处理空位必须收口是 [D2.4](./TEAM_DECISIONS_2026-09-28.md) 的候选验收断言，仍待教师端设计评审；关闭后可保留空位/未分配学生，但必须记录原因。
- 激活码具体发放、补发和账号恢复，退选/纠错优先级，冻结失败重试与可靠性恢复时限须由对应模块负责人定稿。
- 真实部署地址、数据库与浏览器版本、真实班级规模、教师具名意见，以及权限、性能、易用性和兼容性结果尚无证据，不能写成已实现或已通过。
