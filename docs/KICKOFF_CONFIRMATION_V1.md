# CourseMatch 第一周立项会确认版

> 状态：待真实立项会全员确认。本文用于会议讨论和确认；会议结束后须补写实际时间、参会人、会议结论与照片位置，不能以本文替代真实会议记录。

## 1. 项目基本信息

- 课程官方选题：学生选题系统
- 项目名称：CourseMatch
- 项目形式：Web 应用
- 要解决的问题：当多名学生竞争有限题目时，让选题过程做到规则公开、过程可复核、结果可解释。

## 2. 最终 MVP

第一版不是“题目展示 + 报名表”，而是一套可演示的公平选题分配闭环：

```text
教师确认参与名单、题目、名额、资格条件和规则
→ 学生浏览题目，提交最多 3 个有序志愿
→ 截止后冻结名单、题目、名额与志愿
→ 系统生成一次随机顺序
→ 按顺序逐个学生尝试第 1、2、3 志愿
→ 未分配学生进入待补选；剩余题目形成补选池
→ 公布个人结果、处理原因和题目名额使用情况
→ 教师仅处理预定义异常，并留下调整记录
```

### 第一版必须完成

1. 教师创建选题活动，确认本轮参与学生名单。
2. 教师维护 5～10 个题目的说明、名额与硬性资格条件。
3. 教师在开放前公布截止时间、分配规则、补选规则与调整边界。
4. 学生浏览题目、查看计划名额/汇总热度，提交最多 3 个不重复的有序志愿。
5. 截止后系统冻结数据，生成一次随机顺序，并按“学生顺序 → 志愿顺序 → 名额”执行分配。
6. 学生查看自己的随机序号、志愿处理原因、个人结果；公共区域仅展示题目名额汇总。
7. 三个志愿均失败的学生进入补选池；补选冲突沿用原随机顺序。
8. 教师只能处理退选、题目取消、资格信息错误、硬性要求不匹配等异常，且必须记录原因和名额影响。

### 第一版不做

- 多套可切换分配算法、AI 自动决定结果；
- 学生互换题目、即时聊天、支付、完整教务系统；
- 公开其他学生的完整志愿；
- 应用商店上架或原生 App；
- 未经记录的人工插队或反复重新抽签。

## 4. NABCD

### N Need

课程选题常依赖 Excel、问卷和群聊。当多人希望选择同一题目时，学生难以知道题目竞争情况和结果依据，教师需要手工汇总、反复协调，容易产生“先到先得”“老师偏心”或结果难以解释的疑问。

### A Approach

做一个轻量 Web 系统。教师先确认参与名单，并在填报前公开题目、名额、资格条件、截止时间和唯一分配规则；学生提交有序志愿；截止后系统一次性生成随机顺序，按顺序逐人尝试志愿。未分配者进入补选，教师对异常调整留下可审计记录。

### B Benefit

- 学生：无需反复在群里询问，能知道规则、自己的结果和具体原因。
- 教师：减少手工汇总与反复协调，获得题目、名额和异常处理的统一视图。
- 课程小组：能完整展示需求、原型、数据状态、算法、测试、部署与真实反馈过程。

### C Competitors Alternatives

Excel、问卷、在线文档和群聊可以收集意向，但无法可靠冻结规则、自动限制名额、解释分配过程或记录调整。普通报名审批系统也容易变成教师逐个决定。CourseMatch 的差异是：在填报前固定一套可复核的分配机制，并将补选与异常调整纳入流程。

### D Delivery

交付一个可公开访问的 Web 演示：教师创建活动与题目，学生填写志愿，系统完成一次可解释分配，未分配学生进入补选，双方查看结果。Gitee 保存立项、需求、原型、任务计划、代码、测试和用户反馈证据；项目最后通过网页提供访问和使用说明。

│   └── 记录异常调整
├── 学生端
│   ├── 浏览题库与规则
│   ├── 填写最多 3 个有序志愿

│   └── 未分配时参与补选
