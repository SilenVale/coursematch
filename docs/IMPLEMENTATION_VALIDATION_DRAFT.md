# CourseMatch 输入输出与验收执行草案

> 状态：2026-09-24 的**个人设计输入建议，待团队审阅**；不是需求基线、已实现接口、已执行测试或教师认可的指标。适用依据：[需求基线](./REQUIREMENTS_ANALYSIS.md) FR-01～09、AC-01～09，以及个人报告 FR-10/11、BR-04～07、T01～13。若有冲突，以团队需求基线为准并提交待决问题，不暗中改规则。本稿使用语义字段和错误类别，不预设 URL、HTTP 状态、数据库或框架。

## 1. 字段与反馈约定（拟议）

| 操作 | 最少输入和约束 | 成功反馈 | 失败时不应改变 |
|---|---|---|---|
| 开放活动 | 教师身份、`activityId`；`startAt < deadlineAt`（均含时区）；名单、题目、规则非空；`maxPreferences` 为 1～3 | `activityId`、状态 `filling`、`ruleVersion`、开放时间 | 活动保持草稿，不能部分开放 |
| 发布题目 | `topicId`、题目名称/说明、`capacity` 正整数、可判定的资格条件 | `topicId`、发布状态、名额及资格摘要 | 已发布题库与影响公平的字段不变 |
| 保存志愿 | `activityId`、由服务端识别的本人身份、`orderedTopicIds`：1～活动上限个已发布、不重复且有序的 ID；服务端收到时刻 `< deadlineAt` | `orderedTopicIds`、含时区的 `submittedAt`、当前有效版本标识（具体编码待设计） | 最后一次**有效**志愿不被非法、逾期或超时响应覆盖；网络超时先查当前有效版本再决定是否重试 |
| 截止冻结 | 教师可查询，冻结动作须基于活动截止与一致性约束；保存名单、题目、资格、规则、有效志愿与随机序号 | 不可变的快照标识、状态 `frozen`、摘要 | 失败不产生半冻结快照或部分随机序号 |
| 主分配 | 有权限教师、`activityId`、已冻结快照标识 | 唯一 `batchId`、执行时间、名额和结果汇总；重复请求返回**同一批次** | 不重复扣减名额、不重新抽取序号、不改快照 |
| 查看结果 | 由服务端识别的本人身份及 `activityId`（或授权教师查询活动汇总） | 本人结果、命中轮次/失败原因；未提交明确显示“未提交”属于个人建议 | 不暴露其他学生具体志愿或个人结果 |
| 补选意愿（个人建议） | 待补选者、一个当前有余量且满足资格的 `topicId`；统一截止前最后一次有效意愿 | 当前有效意愿与提交时间；不即时占位；到点集中结算沿用冻结序号 | 无效、逾期或网络失败不覆盖已有有效意愿 |
| 异常调整 | 授权教师、预定义异常类型、非空原因、目标学生/题目和预期变更 | 调整前后、操作人、时间、名额影响及审计记录标识 | 无效/超额/重复分配时，不改变结果或原冻结快照 |

数据边界：时间统一携带时区，页面显示北京时间（个人建议），截止以服务端接收时刻判定；本人身份不由前端传入任意学生 ID 即获授权。个人报告中的 `activityId`、`topicId`、`batchId`、`ruleVersion` 为语义字段，不宣称已有实体格式、API 或存储结构。

### 建议的稳定错误类别（非已实现响应码）

| 类别 | 触发条件 | 可观察期望及后置状态 | 映射 |
|---|---|---|---|
| `NOT_PARTICIPANT` | 不在本活动名单仍试图提交志愿 | 拒绝并提示参与资格；已有有效志愿不变 | FR-04、T05 |
| `FORBIDDEN_OWNER` | 学生 B 读取/修改学生 A 的个人数据，或学生触发教师操作 | 服务端拒绝，不返回他人内容；本次无状态变更 | FR-11、NFR-01、T10（个人补充） |
| `MISSING_REQUIRED` | 开放活动缺名单、题目、截止或规则 | 指明缺失字段；活动仍为草稿 | FR-01、T01 |
| `INVALID_CAPACITY` | 名额为 0、负数、非整数 | 拒绝并指出名额字段；现有值不变 | FR-02、T02 |
| `DUPLICATE_TOPIC` | 一次志愿提交包含重复题目 | 拒绝；原有效志愿不变 | FR-04、T04 |
| `PREFERENCE_COUNT` | 志愿为空或超过本活动上限 | 拒绝并显示允许数量；原有效志愿不变 | FR-04、T04 |
| `TOPIC_UNAVAILABLE` | 志愿题目不存在、未发布或不属于本活动 | 拒绝并指明无效项；原有效志愿不变 | FR-03/04、T04 |
| `DEADLINE_REACHED` | 服务端收到时间恰好到点或更晚 | 拒绝新提交；旧有效提交与冻结快照不变 | BR-06、T05（个人建议） |
| `STATE_CONFLICT` | 未冻结就请求分配；开放后直接修改公平性字段 | 拒绝并指出当前状态；原状态与数据不变 | FR-01/05/06、T01/T07 |
| `SUPPLEMENT_NOT_ELIGIBLE` | 非待补选者提交、题目无余量或不合资格 | 拒绝并指出对应条件；旧有效意愿不变 | FR-08、T09/T13（部分待确认） |
| `ADJUSTMENT_REJECTED` | 无预定义原因、会超名额或导致一人两题 | 拒绝并显示约束；原结果与原快照不变 | FR-09、T11 |

错误类别用于对齐需求与测试，不等于约定已实现的字符串常量。多个错误同时发生时的优先顺序、网络重试的幂等键、错误信息中可披露的个人数据，均需教师端/学生端负责人在设计阶段统一。已合法重复触发主分配应返回原 `batchId`，**不**属于 `STATE_CONFLICT`。

## 2. 可复现的最小测试数据（全部虚构）

先创建独立测试活动，题目甲、乙各 1 位，`maxPreferences = 2`；参与者 A、B、C 的冻结序号分别为 03、02、01。A 填 `[甲]`，B 填 `[乙,甲]`，C 填 `[乙]`；另设不在名单内的 D 与不同身份的学生 E。冻结序号应由测试夹具控制或用可观察快照指定，**不能在正式分配时人为重抽**。此例是断言数据，不是某班实际规模。

| 用例 | 前置、操作与应记录的证据 | 预期结果（尚未执行） |
|---|---|---|
| T04 志愿保持 | 填报期 A 依次提交 `[甲,乙]`、重复的 `[甲,甲]`、合法的 `[乙,甲]`、空列表；每次保存输入、服务端反馈与随后读取的当前有效版本；模拟一次请求超时后先查询，不把超时当成功 | 只有两次合法提交更新版本，最终 `[乙,甲]`；非法输入不覆盖；超时由查询结果确认是否成功 |
| T05 截止边界 | 用可控的**服务端接收时刻**分别设为截止前 1 ms、恰好截止、截止后 1 ms；D 作为非参与者提交；记录带时区时间、身份、请求/拒绝类别、冻结前后快照摘要 | 仅合法参与者且早于截止的请求可生效；D 为 `NOT_PARTICIPANT`；恰好/晚于截止为 `DEADLINE_REACHED`；旧志愿与快照不变 |
| T06 轮次优先 | 在上面的 A/B/C 固定数据上冻结并执行一次分配，保存每轮候选、名额、序号与批次 | 第一轮 A 得甲、C 得乙；第二轮 B 不能凭 02 序号挤掉 A 的第一志愿；两题均不超额 |
| T07 幂等及冲突 | 另建题目丙 2 位、同轮 4 位争夺，1 位不符资格；执行主分配两次，比较两次 `batchId`、结果、名额数、快照摘要 | 先剔不合格者，其余按冻结序号选前 2 位；重复触发返回相同批次和数据；无第二批次 |
| T10 越权 | 分别使用教师、A、E 身份读取 A 的志愿/结果与活动汇总，让 E 尝试请求 A 的数据、普通学生触发教师动作；保存脱敏请求/响应 | E 无法获取 A 的个人数据；学生不能操作教师活动；公开汇总不含个人志愿明细；均由服务端校验，不靠隐藏按钮 |
| T09/T13 补选（个人建议） | 另建待补选者 P、Q，剩余题目丁 1 位、戊 1 位；P 截止前先选戊后改选丁，Q 也选丁；再模拟无余量、一次多题、到点后提交；保存意愿版本和结算前后名额 | 戊不是 P 的最终意愿；无效/逾期不覆盖丁；提交不立即占位；统一截止后 P/Q 仅一人按冻结序号得到丁，另一人未分配；**团队确认后才成为正式验收** |
| T11 调整（部分个人建议） | 教师分别发起无原因、满额加入、重复分配和合法预定义异常；保存拒绝类别、调整前后与操作日志 | 非法动作拒绝；合法动作留痕且不改原冻结快照；补选结束后新增空位先待处理的细则**待团队确认** |

## 3. 非功能测试执行记录模板（无测试结果）

| 填写项 | 实际执行时必须记录；未确定不填猜测值 |
|---|---|
| 版本与批准 | GitHub 提交、需求/阈值获团队确认的记录与日期；未确认时只做探索性测量 |
| 环境 | 执行日期/时区、客户端机型和系统、浏览器、网络类型/位置、服务端配置与部署地址（敏感地址脱敏）、数据库和数据初始化方式 |
| 数据量 | 实际参与者人数、题目数、名额、资格组合；30 人/10 题仅为原报告的示例负载，不是已调查的班级规模 |
| 请求样本 | 同一固定环境分别记录题目查询与合法志愿提交各至少 20 次：每次输入摘要、服务端开始/结束时刻、耗时、成败、失败原因；提交须在独立测试活动/可重置数据上执行 |
| 结果判定 | 若团队正式采用 NFR-04：每类 20 次至少 19 次 ≤2 秒，并记录失败次数与请求成功率；主分配在新测试活动中一次 ≤5 秒。不得仅挑最快一次或把需求数值当作实测 |
| 易用性 | 若团队正式采用 NFR-05：找 3 位未参与设计者，分别记录是否在无提示下完成“找规则→排序提交→解释结果”、耗时、卡点分类（规则/交互/文案/其他）及自愿提供的匿名原话；至少 2/3 完成才达到拟议线 |
| 权限/时间 | 保存 T05/T10 的脱敏请求、响应、服务端时钟与快照对比；用户身份和访问令牌不得放进公开仓库 |

执行人应在可运行系统出现后附原始结果文件、环境说明、测试日期和结论；目前以上均为**执行步骤与模板**，没有可展示的实测通过记录。静态 Demo 的交互试测不能代替服务端权限或性能验证。
