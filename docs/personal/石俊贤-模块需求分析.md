## 3.1 模块目标

### 用户

**课程教师**。一次选题活动只有一位负责教师，他只操作自己创建的活动。

### 在什么状态下做什么

M2 覆盖活动生命周期前半段的两态：

| 活动状态 | 教师在本模块能做什么 |
|---|---|
| 草稿（`DRAFT`） | 配置一切：名称、说明、起止时间、最大志愿数、参与名单、题目、名额、资格条件 |
| 已发布（`PUBLISHED`） | 只读查看；仅可修改「活动说明」，可作废活动 |

### 成功后得到什么结果

一次**可公开、可复核、不可篡改起点**的交付：

1. 学生名单与题目在一次事务里整体落库，不存在「半份名单」或「配了一半的题目」；
2. 所有影响分配的字段（名单、题目、名额、资格、时间、志愿数）在发布前固定，发布后被服务端锁定；
3. 发布这一刻的配置被 `configVersion` 与 `published_at` 标记，成为后续冻结快照的输入起点。

### 为什么这个模块值得单独做

选题系统最常见的争议不是分配算法，而是**「名单里到底有谁」和「题目名额到底是多少」事后说不清**。M2 的核心价值不是「能把题目填进去」，而是让这两件事在发布前就是确定的、可追溯的：

- 名单只接受五列结构化数据，整份替换，失败不动旧数据；
- 任何配置变更都递增 `configVersion`，形成一条可审查的版本链；
- 发布是一次显式的、带齐备性校验的状态跃迁，不是「点保存就算上线」。

## 3.2 具体业务逻辑

按「输入 → 校验/判断 → 系统处理 → 页面反馈」逐一说明本模块的 6 个关键动作。

### 一、创建活动草稿

| 环节 | 内容 |
|---|---|
| 输入 | 活动名称、活动说明、开始时间、截止时间、最大志愿数（1～3） |
| 校验/判断 | ① 五个字段全部必填；② 标题 1～120 字，说明 ≤2000 字；③ 最大志愿数是 1～3 的整数；④ 时间是合法 ISO 8601；⑤ **截止时间必须晚于开始时间** |
| 系统处理 | 校验全部通过才落库，`lifecycle='DRAFT'`、`config_version=0`、`owner_account_id` 取会话账号（不取请求体，防止越权建活动） |
| 页面反馈 | 成功：新活动出现在左侧列表并被自动选中；失败：字段级红字提示，错误码 `INVALID_INPUT` + `fieldErrors` |

**设计判断**：时间先后关系在服务端再校验一次。浏览器端的 `datetime-local` 控件不阻止教师把截止时间填在开始时间之前。

### 二、编辑活动基本信息

| 环节 | 内容 |
|---|---|
| 输入 | 任意一个或多个可编辑字段 + `expectedConfigVersion` |
| 校验/判断 | ① 归属校验：非本人活动一律返回 404（不透露活动是否存在）；② 生命周期校验：`VOID`/`CLOSED` 不可改；③ **乐观锁**：`expectedConfigVersion` 必须等于当前 `config_version`，否则 409 `VERSION_CONFLICT`；④ **发布后字段锁定**：只允许改 `description`，改其他字段返回 409 `CONFIG_LOCKED`；⑤ 字段级校验同创建 |
| 系统处理 | `UPDATE ... SET ..., config_version = config_version + 1`，一次请求只递增一次版本 |
| 页面反馈 | 成功：表单以服务端返回值回填、版本号 +1；失败：版本冲突提示「请刷新后重试」，字段锁定提示具体哪些字段被禁止 |

**设计判断：为什么只提交改动过的字段。**
契约里 `ActivityPatchInput` 要求「至少一个字段」。如果前端全量提交，服务端无法区分「教师改了标题」和「教师只是保存了表单」，审计日志里的 `changedFields` 就失去意义。因此前端用基线值做 diff，只发送真正变化的字段；服务端仍会独立校验，不信任前端。

### 三、导入参与名单（五列 CSV）

这是本模块最复杂的一步，拆成「预览」与「替换」两个接口。

**第 1 步：预览（`POST .../participants/preview`，不写库）**

| 环节 | 内容 |
|---|---|
| 输入 | CSV 文件内容（`text/csv` 裸文本或 multipart）+ `expectedConfigVersion` |
| 校验/判断 | ① 版本锁；② 文件非空、行数 ≤5000；③ **每行必须恰好 5 列**：学号、姓名、入学年、专业、班级；④ 各列非空；⑤ 入学年必须是 4 位数字；⑥ **文件内学号不得重复**；⑦ 若学号已存在于学生档案，五列信息必须与档案一致，否则报 `PROFILE_MISMATCH` |
| 系统处理 | 只计算差异，不落库。返回 `addedCount` / `removedCount` / `retainedCount` 以及逐行的 `ADDED` 或 `RETAINED` 标记 |
| 页面反馈 | 显示「新增 N / 保留 M / 移除 K」三个标签与逐行变化表；若有行错误，**逐行列出行号、字段、原因**，并明确提示「已生效名单未被修改」 |

**第 2 步：整份替换（`PUT .../participants`）**

| 环节 | 内容 |
|---|---|
| 输入 | 同预览，外加预期的 `expectedConfigVersion` |
| 校验/判断 | 除预览的全部校验外：① 活动必须仍是草稿（否则 409 `CONFIG_LOCKED`）；② 在**事务内**用 `SELECT ... FOR UPDATE` 锁住活动行，再校验一次版本，避免两个浏览器同时替换互相覆盖 |
| 系统处理 | 事务内依次：为新学号建学生档案 → `DELETE` 该活动全部参与记录 → 按文件顺序批量 `INSERT` → `config_version + 1` → `COMMIT` |
| 页面反馈 | 成功：绿色提示「当前 N 人，配置版本升至 vN」，名单表刷新；失败：错误展示 + 旧名单完好 |

**设计判断：为什么是「整份替换」而不是「增量增删」。**
增量接口需要处理「新增一个已在名单的人」「删除一个已提交志愿的人」等状态组合，且两次增量之间名单可能处在中间态。整份替换让「文件内容 = 系统状态」成为一条不变量，教师手上有 Excel 时操作也最自然。代价是名单规模受限（5000 行），对课程选题场景足够。

**设计判断：为什么学生档案冲突要报错而不是静默更新。**
`student_profile` 是全库共享表，同一名学生可能同时出现在多个活动的名单里。若某次导入把「软件工程 1 班」写成「软件工程 2 班」并静默覆盖，会改到别的活动。因此冲突一律拒绝，要求教师确认后再改文件。

**失败不破坏旧名单的三道保险**：
1. 解析与逐行校验是纯函数，在任何数据库操作之前完成；
2. 解析失败直接返回，连事务都不开启；
3. 即使进入事务，任何异常都 `ROLLBACK`。

### 四、题目与名额配置

| 环节 | 内容 |
|---|---|
| 输入 | 题目名称、简介、标签（≤8 个，单个 ≤24 字）、名额（正整数，≤1000）、资格模式、资格说明 |
| 校验/判断 | ① 活动必须是草稿；② 版本锁；③ 名额必须是正整数（`CHECK (capacity > 0)` 在数据库再兜一层）；④ 资格模式为 `ALL` 时不允许带限定名单，为 `EXPLICIT` 时**必须**至少指定一人；⑤ 限定名单里的 `participantId` 必须属于本活动名单 |
| 系统处理 | 事务内写 `topic`，`EXPLICIT` 时整体重写 `topic_eligible_participant`，`config_version + 1` |
| 页面反馈 | 列表显示题目、标签、容量、资格（ALL 显示「名单内全体」，EXPLICIT 显示「限定 N 人」）、热度；错误按字段提示 |

**设计判断：资格模式为什么用联合类型而不是布尔标志。**
契约里 `TopicInput` 写成 `{ eligibilityMode: "ALL" } | { eligibilityMode: "EXPLICIT"; eligibleParticipantIds: Id[] }`。这让「EXPLICIT 但没有名单」在类型层就不可能构造出来，服务端校验只是防御性兜底，而不是唯一防线。前端表单也据此切换：选 ALL 时清空勾选。

**已知耦合风险（已在代码中兜底）**：限定名单存的是 `participant.id`。名单整份替换时旧 `participant` 行会被删除，限定引用随之悬空。发布前的齐备性检查会检出「EXPLICIT 但限定名单为空」的题目并拒绝发布，避免发布出一个没人能选的题目。

### 五、发布活动

| 环节 | 内容 |
|---|---|
| 输入 | `expectedConfigVersion` |
| 校验/判断 | ① 必须是草稿；② 版本锁；③ **齐备性检查**：名称非空、开始早于截止、志愿数 1～3、**名单非空**、**至少一个题目**、无悬空的限定名单 |
| 系统处理 | `UPDATE activity SET lifecycle='PUBLISHED', published_at=NOW(), config_version+1 WHERE id=$1 AND lifecycle='DRAFT'`，用条件更新防止并发重复发布 |
| 页面反馈 | 成功：状态标签变「已发布」，配置区变只读，题目与名单区出现锁定说明；失败：列出未通过的检查项 |

**设计判断：页面清单只是提示，判定在服务端。**
前端「发布前检查」面板会把未通过项标红并禁用按钮，但这是一份**给人的提示**，不是授权依据。服务端 `publishBlockers()` 独立重算同一套规则。两者规则来源相同但实现独立，页面被绕过时仍然安全——这同时满足 V1 优秀线第 5 条「未齐备不能发布」和「服务端权威」。

### 六、作废活动

| 环节 | 内容 |
|---|---|
| 输入 | 作废原因（必填，≤500 字） |
| 校验/判断 | ① 归属；② **只有「已发布且尚未成功分配」可以作废**；③ 原因必填；④ 条件更新 `WHERE lifecycle='PUBLISHED'` 防止并发 |
| 系统处理 | `lifecycle='VOID'`，写入 `void_at` / `void_reason`，版本 +1。原活动保留不删除 |
| 页面反馈 | 成功：显示作废时间与原因；失败：提示当前状态不允许作废 |

**设计判断：为什么是「作废」而不是「删除」或「重置回草稿」。**
作废保留全部历史，学生仍能看到这个活动曾经存在（只是不可再填），符合「结果可解释」的总体目标。重置回草稿会让「已经看到题目并填过志愿」的学生面对一份内容突变的配置，无法解释。作废后教师另建新活动、学生重新提交，代价可控。

## 3.3 页面与状态

页面：`/teacher/config`，一个页面内用左侧活动列表 + 右侧分区面板布局。

### 页面区块

| 区块 | 组件 | 说明 |
|---|---|---|
| 活动侧栏 | `ActivityConfigPage` | 列出本人全部活动，显示标题、生命周期、阶段、截止时间 |
| 新建草稿 | `CreateActivityForm` | 默认开始=现在、截止=7 天后 |
| 基本信息 | `ActivityBasicsForm` | 只提交改动字段 |
| 参与名单 | `RosterPanel` | 导入区（仅草稿）+ 当前名单（含筛选） |
| 题目与名额 | `TopicPanel` | 列表 + 新建/编辑/删除表单 |
| 发布前检查 | `PublishPanel` | 五项清单 + 发布 / 作废 |

### 正常状态

- 草稿活动：所有字段可编辑，名单导入区可见，题目可增删改，发布前检查五项全绿，发布按钮可用。
- 已发布活动：字段灰化，名单区显示「活动已不是草稿状态，名单只能查看、不能替换」，题目区隐藏编辑/删除按钮，发布按钮禁用，出现「作废活动」。

### 空状态

- 无任何活动：「还没有活动。点「新建活动」创建第一个草稿。」
- 名单为空：「名单为空。导入 CSV 后学生才能看到并选择本活动的题目。」
- 题目为空：「还没有题目。每个题目需要名称、简介、标签、容量和资格条件。」
- 筛选无结果：表格渲染为空，筛选条件保留。

### 异常 / 禁用状态

| 场景 | 页面表现 |
|---|---|
| CSV 有行错误 | 红色横幅显示 `IMPORT_INVALID` + 「共 N 处问题；已生效名单未被修改」，下方逐行表格（行号/字段/原因），超过 20 行折叠；「确认替换」保持禁用 |
| 版本冲突 | 横幅提示当前版本与你提交的版本，提示刷新；已有预览丢弃，要求重新预览 |
| 发布后试图改标题 | 服务端返回 `CONFIG_LOCKED` 并点名被锁字段；页面上该输入框本就已禁用 |
| 题目接口未落地（501） | 题目区显示「待接入」说明与原因，**不显示为空列表**——避免教师误以为题目真的没配 |
| 已作废 / 已关闭 | 隐藏齐备性清单（此时发布已无意义），提示「只有已发布且尚未成功分配的活动可以作废」 |
| 未登录 / 非教师 | 路由守卫重定向到首页 |

**设计判断：「501 显示为待接入而不是空列表」。**
这是联调期真实踩到的坑。接口未实现时返回 501，如果前端把任何错误都渲染成空数组，教师会以为「我配的题目丢了」。空状态和错误状态必须视觉上可区分。

## 3.4 数据与接口边界

### 关键数据字段

**活动（`activity`）**

| 字段 | 类型 | 约束 / 说明 |
|---|---|---|
| `id` | UUID | 主键 |
| `owner_account_id` | UUID | 归属教师，**授权唯一依据** |
| `title` | TEXT | 非空，≤120 字 |
| `description` | TEXT | 默认 `''`；发布后仍可改的唯一字段 |
| `start_at` / `deadline_at` | TIMESTAMPTZ | 必须 `start_at < deadline_at` |
| `max_preferences` | INT | `CHECK BETWEEN 1 AND 3` |
| `rule_version` | TEXT | 默认 `cm-rule-v1`，冻结时写入快照 |
| `lifecycle` | TEXT | `DRAFT` / `PUBLISHED` / `ALLOCATED` / `CLOSED` / `VOID` |
| `config_version` | INT | 每次配置变更 +1，乐观锁依据 |
| `published_at` | TIMESTAMPTZ | 发布时刻 |
| `void_at` / `void_reason` | TIMESTAMPTZ / TEXT | 作废信息（迁移 002） |

**题目（`topic`，迁移 002）**

| 字段 | 类型 | 约束 |
|---|---|---|
| `id` | UUID | 主键 |
| `activity_id` | UUID | `ON DELETE CASCADE` |
| `title` | TEXT | 非空 |
| `tags` | TEXT[] | 默认 `'{}'` |
| `capacity` | INT | `CHECK (capacity > 0)` |
| `eligibility_mode` | TEXT | `CHECK IN ('ALL','EXPLICIT')` |
| `eligibility_description` | TEXT | 给学生看的资格说明 |
| `created_at` | TIMESTAMPTZ | 列表排序依据 |

**限定名单（`topic_eligible_participant`）**：`(topic_id, participant_id)` 复合主键，双向 `ON DELETE CASCADE`。

**参与名单（`participant`）**：`(activity_id, student_profile_id)` 唯一；M2 只负责替换整份名单，`eligible` 默认 `TRUE`。

### 前端调用什么

| 接口 | 何时调用 |
|---|---|
| `GET /api/activities` | 进入页面、任何写操作后刷新侧栏 |
| `POST /api/activities` | 新建草稿 |
| `GET /api/activities/:id` | 选中活动 |
| `PATCH /api/activities/:id` | 保存基本信息 |
| `GET /api/activities/:id/participants` | 名单区与发布前检查的人数统计 |
| `POST .../participants/preview` | 点「预览名单」 |
| `PUT .../participants` | 点「确认替换」 |
| `GET/POST/PATCH/DELETE .../topics` | 题目区 |
| `POST .../publish` | 发布 |
| `POST .../void` | 作废 |

所有写请求带 `X-CourseMatch-Request: 1` 且 `Origin` 必须匹配 `WEB_ORIGIN`（CSRF 防护）。

### 后端必须保证什么

1. **授权只认会话**。`owner_account_id` 来自 `req.actor.accountId`，绝不取请求体里的「owner」字段；非本人活动返回 404 而非 403。
2. **事务完整性**。名单替换、题目增删改、发布、作废都在事务内完成，失败整体回滚。
3. **乐观锁强制执行**。每次写操作都校验 `expectedConfigVersion`，防止两个窗口同时编辑互相覆盖。
4. **发布后锁定**。服务端拒绝修改影响公平性的字段，不依赖前端禁用按钮。
5. **不越界计算**。M2 不计算任何分配结果、不生成随机序号、不写冻结快照——这些是 M4/M5 的职责。

### 前端不得做什么

- 不得把本地未保存的表单当作已保存配置展示；
- 不得自行判定活动能否发布（只做提示，判定以服务端为准）；
- 不得自行推导「已生效名单」，一律以服务端返回为准；
- 不得在浏览器端计算名额占用或分配结果。

## 3.5 异常与验收

### 边界场景与可验证通过条件

| # | 场景 | 输入 | 期望结果 | 验证方式 |
|---|---|---|---|---|
| 1 | **截止时间早于开始时间** | `startAt=明天, deadlineAt=今天` | 400 `INVALID_INPUT`，`fieldErrors` 指向 `deadlineAt`，不落库 | 接口测试；页面在「截止时间」下方显示红字 |

## 3.6 创意提案

### 创意一：发布前规则自检清单（已落地）

- **解决的具体问题**：教师漏配名单或题目就点发布，导致学生进来看不到任何题目；传统做法是靠教师自己记得检查。
- **受益用户**：教师。
- **用户在什么时刻使用**：草稿配置完成后、点「发布活动」之前。
- **交互或页面表现**：发布区内五条清单，每条显示通过 / 未通过 / 未知与具体数值（如「参与名单：3 人」「题目与名额：2 个题目」）；未通过时按钮禁用并汇总「还有 1 项未通过：题目与名额」。
- **需要的数据与关键判断**：活动字段、名单人数、题目数量、EXPLICIT 题目的限定名单是否为空。判断「名称非空、开始早于截止、志愿数 1～3、名单非空、至少一个题目、无悬空限定名单」六条。
- **与共同基线的关系**：不改变基线。直接支撑 AC-01「开放活动」。
- **如何在 HTML Demo 中展示**：在教师配置页底部固定一个清单区，逐项打勾；故意删光题目后展示「未通过」状态。
- **如何测试是否有效**：清空题目 → 清单显示未通过且按钮禁用 → 绕过页面直接调接口 → 服务端同样返回 400。两条都通过才算有效。
- **实现成本**：低。规则集中在一个 `buildChecklist` 函数与一个 `publishBlockers` 函数，无新增表、无新增接口。
- **风险或隐私影响**：清单显示名单人数，仅教师可见，无隐私问题。风险在于「页面提示」与「服务端判定」若不同步会产生误导，因此两者共用同一组规则常量。

### 创意二：名单导入差异预览与不可破坏性保障

- **解决的具体问题**：整份替换是个高危操作——教师上传错误文件会一次性删光名单。传统 Excel 方案要么没有撤销，要么需要重新手工录入。
- **受益用户**：教师。
- **用户在什么时刻使用**：每学期导入选课学生名单时。
- **交互或页面表现**：选文件或粘贴后点「预览名单」，页面显示「新增 N / 保留 M / 移除 K」三个徽标与逐行变化表（每行标注「新增」或「保留」）；有行错误时列出每一行的具体原因且不允许确认；移除人数大于 0 时额外提示「替换后会有 K 人从名单中移除」。
- **需要的数据与关键判断**：现有名单与待导入名单的学号集合差集；逐行格式校验；学生档案一致性校验。
- **与共同基线的关系**：不改变基线。支撑 AC-01 的「参与名单」完整性要求。
- **如何在 HTML Demo 中展示**：上传一份减少两人的名单预览，标出「移除 2」后再点确认，演示名单变化。
- **如何测试是否有效**：① 坏 CSV 预览后 `participant` 表行数不变；② 预览后直接刷新页面，名单内容未变（证明预览确实不写库）；③ 先成功替换再替换失败，旧名单仍在。
- **实现成本**：中。需要纯函数解析器（已实现，20 条单测）+ 事务替换 + 前端差异表。
- **风险或隐私影响**：预览接口返回学生姓名与学号，仅活动拥有教师可调用，非本人活动返回 404。移除人数提示存在误判可能（例如教师本想新增而非替换），已在页面文案中说明「整份替换」语义。

### 创意三：配置版本链与并发编辑提示（部分落地）

- **解决的具体问题**：两位教师共用账号、或同一教师开了两个浏览器窗口时，后保存的一方会静默覆盖前一方。选题配置一旦被覆盖，难以发现被改了哪一项。
- **受益用户**：教师；间接保护学生看到的配置确实是被教师确认过的那份。
- **用户在什么时刻使用**：多人协作编辑、或长时间打开页面后再次保存时。
- **交互或页面表现**：页面右上角常驻「配置版本 vN」；保存失败时提示「配置已被修改（当前版本 3，你提交的是 2），请刷新后重试」，已失效的名单预览被丢弃、要求重新预览。
- **需要的数据与关键判断**：`config_version` 单调递增；每次写操作携带 `expectedConfigVersion`；服务端条件更新。
- **与共同基线的关系**：不改变基线。为 M4/M5 的冻结快照提供「配置在冻结前是确定的」这一前提。
- **如何在 HTML Demo 中展示**：两个窗口同时打开同一活动，A 保存后 B 再保存，B 看到冲突提示。
- **如何测试是否有效**：用过期版本号调用 PATCH 返回 409；并发替换名单时只有一个成功。
- **实现成本**：低。版本字段与条件更新已实现；后续若要显示「谁在什么时候改了什么」，需要操作日志表，成本升级为中。
- **风险或隐私影响**：无。当前实现只提示冲突，不记录变更历史，需在 V2 评估是否增加操作日志。
