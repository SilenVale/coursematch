## 1. 问题与目标

课程选题常以 Excel、问卷和群聊收集意向。当多人竞争有限题目时，学生难以获知规则和结果依据，教师需要手工汇总与协调，容易引发对“先到先得”或人工偏好的质疑。

CourseMatch 是一个面向课程选题活动的 Web 系统。它让教师在填报前公开参与范围、题目、每题名额、资格条件、截止时间和唯一分配规则；让学生提交有序志愿；在截止后按公开规则完成一次分配，并向学生解释结果。

本系统的目标是：

1. 规则公开：所有影响分配的规则在填报前公布。
2. 过程可复核：分配所用名单、题目、名额、志愿和随机序号均可冻结保存。
3. 结果可解释：学生能看到自己的随机序号、志愿处理轮次及失败或成功原因。

## 2. 产品范围

### 2.1 第一版包含

- 教师创建一轮选题活动，维护参与学生、题目、题目名额、资格条件和时间；
- 学生浏览题目、计划名额与汇总热度，提交 1 至 3 个有序且不重复的志愿；
- 活动截止后冻结数据，为每位学生生成唯一随机序号；
- 按志愿轮次执行一次自动分配；
- 展示学生个人结果、题目名额使用情况、待补选名单和调整记录；
- 为未分配学生提供仅含剩余名额题目的补选流程；
- 记录预定义异常导致的人工调整及其原因。

### 2.2 第一版不包含

- 项目组 / 组队管理、学生互换题目；
- 多套可切换分配算法、AI 自动决定结果；
- 实时公开其他学生的完整志愿；
- 完整教务系统、支付、即时聊天、原生 App；
- 未留痕的人工插队、重新抽签或重复运行主分配。

## 3. 角色与职责

| 角色 | 系统内职责 |
|---|---|
| 教师 | 配置活动、确认参与名单、维护题目与名额、公开规则、执行一次分配、开启补选、登记异常调整 |
| 学生 | 浏览题目和规则、维护有序志愿、查看个人分配结果及补选状态 |
| 系统 | 校验活动状态、冻结数据和随机序号、按规则分配、记录可解释的处理原因 |

## 4. 术语

| 术语 | 定义 |
|---|---|
| 选题活动 | 一次有明确参与范围、填报时间和分配规则的课程选题过程 |
| 题目名额 | 一个题目可被分配到的学生人数，不表示项目小组数量 |
| 志愿 | 学生按偏好排序的题目列表；第一版最多 3 个，允许少填 |
| 志愿轮次 | 系统处理同一志愿位次的阶段，例如第 1 轮统一处理所有学生的第一志愿 |
| 随机序号 | 截止后为每位参与学生生成且冻结的唯一序号，仅用于同题、同轮超额竞争 |
| 补选池 | 主分配后仍有剩余名额的题目集合 |
| 待补选 | 所有已填志愿均未成功分配的学生状态 |
| 调整记录 | 教师针对预定义异常进行处理时保存的前后状态、原因和名额影响 |

## 5. 关键业务规则

### 5.1 填报规则

1. 教师可设置一轮活动允许填写的最大志愿数，第一版范围为 1 至 3，默认 3。
2. 学生至少填写 1 个志愿，也可以少于最大数；少填意味着可参与的后续轮次更少，学生自行承担未分配风险。
3. 同一学生的志愿不得重复，排序必须连续。
4. 截止前允许修改；系统只保留最后一次有效提交。
5. 填报期只展示计划名额和汇总热度，志愿提交不预占名额，也不公开其他学生的具体志愿。

### 5.2 冻结规则

活动截止时，系统必须一次性冻结：活动规则版本、参与学生名单、题目、题目名额、资格条件、有效志愿和每位学生的随机序号。冻结后这些数据不能被主分配流程修改。

### 5.3 主分配规则

1. 主分配只允许针对同一份冻结快照执行一次。
2. 第 1 轮处理所有尚未分配学生的第一志愿。
3. 第 2 轮处理第 1 轮后仍未分配学生的第二志愿；第 3 轮同理。
4. 每一轮中，系统按题目分组候选人，先剔除不满足硬性资格条件的学生并记录原因。
5. 对同一题目、同一轮的合格候选人，按随机序号从小到大排序，取剩余名额数量的学生分配该题目。
6. 已分配学生不再参与后续轮次；每名学生最终最多分配一个题目；题目分配人数不得超过名额。
7. 因此，任何学生的第一志愿都必须先于任何学生的第二、第三志愿处理。随机序号不能让某人的第二志愿抢在别人的第一志愿之前。

### 5.4 补选与人工调整

1. 所有已填志愿均失败的学生进入待补选状态，不自动派入不愿接受的题目。
2. 补选池只包含有剩余名额的题目；待补选学生之间竞争同一补选题目时继续沿用冻结随机序号。
3. 教师仅可处理退选、题目取消、资格信息错误、已公开硬性条件不匹配等预定义异常。
4. 每次调整必须记录调整前后、原因、操作人、时间和名额影响，且不能造成重复分配或超额。

## 6. 功能需求

### FR-01 教师创建活动

教师可以创建活动草稿，设置活动名称、开始时间、截止时间、最大志愿数、参与学生名单、题目、题目名额、资格条件、主分配规则和补选规则。系统在开放前校验上述信息完整，开放后禁止直接修改会影响公平性的字段。

### FR-02 题库与名额管理

教师可以新增、编辑和发布题目。每个题目至少包含题目名称、简介、标签、可容纳学生人数和硬性资格条件。名额必须是正整数。

### FR-03 学生题目浏览

填报期内，学生可以浏览已发布题目、题目说明、计划名额、资格条件和汇总热度；可以按关键词或标签筛选。学生端不展示其他学生姓名和具体志愿。

### FR-04 志愿维护与提交

确认参与名单内的学生可以把题目加入志愿、移除志愿和调整顺序。系统限制志愿数不超过活动设置、题目不重复，并在截止前保存学生最后一次有效提交。

### FR-05 截止与冻结

截止后，学生端志愿编辑入口关闭。教师端显示已冻结的数据摘要和随机序号生成状态。系统生成一个不重复的随机序号排列，并保存与活动快照的关联。

### FR-06 执行一次分配

教师可在已截止状态执行“按志愿轮次分配”。系统只能生成一个主分配批次；重复请求必须返回现有结果，不得重新生成随机序号或重新扣减名额。

### FR-07 结果解释

学生可以查看自己的最终题目、命中的志愿位次、随机序号和每一轮的处理原因。典型说明为：“第一志愿有 5 名符合条件学生竞争 2 个名额；你的随机序号为 04，未进入本轮前 2 位；第二志愿在第 2 轮仍有名额，因此分配成功。”

### FR-08 补选

待补选学生可以浏览补选池并提交可接受的题目。系统依据冻结随机序号处理同题冲突。补选结束后，学生结果变为最终确认或仍保持未分配，不能强制分题。

### FR-09 调整记录

教师提交异常调整时，必须选择预定义异常类型并填写原因。系统校验题目名额、学生当前结果和重复分配；成功后生成不可缺失的调整记录。

## 7. 活动状态

| 状态 | 学生可操作 | 教师可操作 | 系统约束 |
|---|---|---|---|
| 未开始 | 仅查看活动说明 | 配置活动与规则 | 草稿可编辑 |
| 填报中 | 浏览、维护、提交志愿 | 查看汇总进度 | 不生成随机序号、不执行分配 |
| 已截止 | 志愿只读 | 查看冻结快照、执行一次分配 | 冻结活动数据和随机序号 |
| 分配完成 | 查看个人结果 | 查看全局结果、开启补选 | 主分配结果锁定，不可重跑 |
| 补选中 | 待补选者选择补选题目 | 查看补选进度、最终确认 | 仅使用剩余名额，沿用冻结序号 |
| 最终确认 | 只读查看结果 | 查看结果与调整记录 | 活动结束 |

完整状态图、页面状态矩阵和交互材料将与本需求文档一同归档到项目 Wiki 的“02 需求分析”和“03 原型设计”目录。

## 8. 分配算法伪代码

```text
输入：冻结后的参与学生、题目名额、资格条件、每名学生的有序志愿

为每名学生生成并保存唯一 lotteryNumber
for rank in 1..maxPreferenceCount:
    candidates = 所有尚未分配且填写了第 rank 志愿的学生
    按第 rank 志愿的题目分组
    for each topicGroup:
        ineligible = 不满足题目资格条件的学生
        为 ineligible 记录资格不符原因

        eligible = 其余学生，按 lotteryNumber 升序
        winners = eligible 的前 topic.remainingSlots 名
        为 winners 分配题目，并扣减名额
        为未入选学生记录同轮名额已满原因

未分配学生 → 待补选
```

## 9. 核心数据对象

| 对象 | 关键字段 |
|---|---|
| Activity | id、名称、开始/截止时间、最大志愿数、状态、规则版本 |
| Participant | activityId、studentId、资格状态、lotteryNumber |
| Topic | activityId、名称、简介、名额、剩余名额、资格条件、发布状态 |
| PreferenceSubmission | activityId、studentId、题目列表、排序、提交时间、是否为最后有效提交 |
| AllocationBatch | activityId、冻结快照版本、执行时间、执行状态、唯一批次标识 |
| AllocationResult | batchId、studentId、topicId、志愿位次、处理轮次、随机序号、结果状态、解释 |
| AdjustmentRecord | 活动、学生、调整前后、原因、操作人、时间、名额影响 |

## 10. 接口边界

第一版前端通过后端接口读取题目、提交志愿、查询个人结果和查看补选池。前端不得自行计算或覆盖分配结果；冻结、随机序号生成、名额扣减、资格校验和分配算法必须在后端事务中执行。

建议接口分组：

- 教师：活动、参与名单、题库、分配、补选、调整记录；
- 学生：题目浏览、志愿提交、个人结果、补选选择；
- 公共：活动规则、题目名额汇总。

## 11. 验收标准

| 编号 | 验收场景 | 通过标准 |
|---|---|---|
| AC-01 | 开放活动 | 缺少题目、名额、参与名单、截止时间或规则时不能开放 |
| AC-02 | 志愿提交 | 学生不能重复选择题目，不能超过最大志愿数，截止前最后一次提交生效 |
| AC-03 | 第一志愿优先 | 任意学生的第一志愿均在任何第二、第三志愿之前处理 |
| AC-04 | 同轮冲突 | 同题同轮超额时，随机序号较小的合格学生获得名额 |
| AC-05 | 资格条件 | 不符合硬性条件的学生不占用题目名额，结果中有明确原因 |
| AC-06 | 名额限制 | 任意题目的最终分配人数不超过其设置名额；任意学生最多一个结果 |
| AC-07 | 可复核 | 分配后能查到冻结快照、随机序号、处理轮次与结果解释，且不能重跑 |
| AC-08 | 补选 | 主分配失败者进入补选池；补选不强制分题且继续沿用冻结序号 |
| AC-09 | 人工调整 | 不满足预定义异常或会导致超额 / 重复分配的调整被拒绝并留下提示 |

## 12. 非功能要求与风险

- 结果解释必须使用学生可以理解的文字，不能只展示“成功 / 失败”。
- 个人端仅显示当前学生的志愿与结果，不公开他人的完整志愿。
- 分配动作需具备幂等性，避免重复点击造成多次分配。
- 关键数据需要保存操作时间和操作人，便于课程演示与测试。
- 当前 HTML Demo 是团队用于验证交互流程的方案；是否可替代墨刀原型，仍需在第三次课向老师确认。
