# 第一版交付规划（优秀线导向）

> **给组员与 Agent 的必读文件。** 实现业务前请先读本文，再读 [ARCHITECTURE.md](./ARCHITECTURE.md) 与 [INTERNAL_MODULES.md](./INTERNAL_MODULES.md)。  
> 架构来源：设计报告 v0.5（平台最高分 98.6）。第 1 版严格按收缩后的首版范围交付，不在此版本实现补选、退选、成功后改结果。

## 一、第一版要做什么

第 1 版的目标是：**一条可公开演示、可写进测试报告与项目报告的真实主链**，不是功能堆满。

### 1.1 业务主链（必须全部走通）

```text
预置账号登录
  → 教师：活动草稿、五列 CSV 名单、题目/容量/资格、发布（或作废）
  → 学生：浏览已发布题目、保存 1～3 个有序志愿（整单提交，不占名额）
  → 截止后：服务端拒写、生成完整冻结快照与每人唯一序号
  → 教师：触发一次主分配
  → 学生：查看本人结果（已分配 / 全落选 / 未提交分开）
  → 教师：查看汇总与证据、填写原因后关闭（可保留空位与未分配）
```

### 1.2 第一版明确不做

- 补选、退选、分配成功后教师改题或改结果  
- 公开注册、学校统一登录、邮件/短信通知  
- 多套分配算法、AI 自动分配、原生 App、支付、完整教务  

以上写在**项目报告第 2 版路线图**里即可，不要塞进第 1 版代码。

### 1.4 优秀线：第 1 版交付勾选（8 条）

答辩与合并 `master` 前，以下 8 条应能**逐项勾选并留证据**（截图、测试记录、PR 链接）：

| # | 交付项 | 通过标准（可观察） |
|---|---|---|
| 1 | **主链端到端** | 干净环境按 README 启动后，教师与学生账号走完 §1.1 全链，数据刷新后仍存在 |
| 2 | **分配规则正确** | `npm test` 通过；且在系统中用 A/B/C/D 四人样例（见 [ALLOCATION.md](./ALLOCATION.md)）可复核；同一快照再次分配返回同一 `batchId` |
| 3 | **服务端权威** | 学生不能读他人志愿/结果；学生不能调用教师写接口；志愿与结果均来自 API，非前端推算 |
| 4 | **截止与冻结** | 截止后新志愿被拒绝；冻结成功前有完整快照；无「半快照」即可分配 |
| 5 | **CSV 与发布** | 名单五列预览/整份替换；失败不破坏旧名单；未齐备不能发布 |
| 6 | **契约一致** | 实现与 `packages/shared` / `api-contracts.ts` 字段与错误码一致；改契约须 PR 说明 |
| 7 | **可公开体验** | 部署 HTTPS 演示地址（或课程要求的公开链接）；README 含账号说明与使用步骤；链接在答辩时可打开 |
| 8 | **过程与质量** | 测试计划 + 用例表（含权限、截止、分配）；至少 1 次组外/真实用户试用记录；GitHub 有各成员可识别的 PR |

未勾满的项：在报告里写清**未测范围与原因**，不要写成「已通过」。

## 二、哪些做法会让后续改进变难（必须避开）

第 1 版按当前架构做，**后续加补选、压测、运维增强会更容易**。下列做法会导致「不是改进，是重写」：

| 禁止做法 | 后果 |
|---|---|
| 在浏览器里抽签、算名额或写最终分配结果 | 无法通过服务端测试；第 2 版补选无法接在同一权威模型上 |
| 截止后直接读当前志愿表分配、不做完整冻结快照 | 无法解释公平性；无法幂等重试；与 98.6 设计不一致 |
| 成功主批次可被覆盖或「悄悄重跑」 | 审计与答辩追问崩盘；补选只能另起炉灶 |
| 三人各做独立前端或独立后端仓库 | 合并成本极高；Cookie、错误格式、路由分裂 |
| 不跟 `api-contracts.ts`，各模块自定字段名 | 联调与回归测试失效 |
| 为赶进度用静态 JSON 冒充已保存志愿/结果 | 演示与真实行为不一致；第七周联调返工 |
| 在 `master` 上直接推、或超大 PR 无验收说明 | 无法追溯谁改了共享迁移/类型 |

**Agent 指令建议：** 若用户要求「先简单前端算一下分配」，应拒绝并指向 `packages/allocation` 与服务端 `POST .../allocation`。

## 三、冲优秀应往哪个方向拓展

优秀不是「第 1 版多塞五个功能」，而是：**主链扎实 + 规则可验证 + 工程过程完整 + 有真实反馈**。

### 3.1 第 1 版就要做满的（冲优秀核心）

1. **可复核的公平**：轮次优先 + 冻结序号；固定样例 + 重复分配幂等。  
2. **可演示的权限与隐私**：越权用例有测试记录。  
3. **可读的失败反馈**：截止、版本冲突、CSV 行错误等返回契约中的 `error.code`。  
4. **可复现的环境**：`migrate` + `seed` + 文档中的启动命令；演示环境与 README 一致。  
5. **真实的用户反馈**：至少数名同学试用（不必凑满 10 人），有原话或操作记录，报告里写是否改需求。  

### 3.2 适合写在「第 2 版 / 后续工作」里（报告与答辩话术）

不在第 1 版代码里硬做，但可体现**架构可扩展**：

| 方向 | 说明 |
|---|---|
| 补选与空位再分配 | 新轮次、新批次；不修改已成功主批次（设计 CH-01 已延期） |
| 性能与并发 | 按 NFR-04 在固定环境压测；报告写指标与是否达标 |
| 改密、限流、备份恢复 | 设计 §9.3 的完整落地与演练 |
| 站内通知、邮件提醒 | FR-12 扩展 |
| 部署与成本 | Zeabur/云主机方案与月费说明 |

答辩时一句话：**第 1 版交付可验证的主链与不可变分配证据；扩展项在契约边界内增量接入，无需推翻数据模型。**

### 3.3 第 2 版路线图（可直接贴进项目报告）

```text
V1（当前）：预置账号 → 配置发布 → 志愿 → 冻结 → 一次主分配 → 本人结果 → 关闭
V2（规划）：在不变更 V1 成功批次的前提下，评估补选轮次、教师异常调整范围、性能基线与备份演练
V3（可选）：通知渠道、与学院身份系统对接（需校方授权与单独评审）
```
