# CourseMatch 第一周立项材料包（待团队审核）

> 状态：草案，供组员及其 AI 审核。本文不是已发生会议的纪要，不能替代真实的参会记录、会议照片或最终团队决议。

## 1. 本次立项要确认什么

课程官方选题为“学生选题系统”，项目工作名称为 **CourseMatch**。

本次会议只需要确认第一版要解决的核心问题：让教师能发布题目和名额，让学生能浏览、填报志愿，让教师能处理申请，并让结果和进度可查询。

本次不确定技术栈、不进入开发排期细节，也不承诺 App、支付、完整教务系统或复杂 AI 自动分配。

## 2. MVP 草案

### 用户与核心任务

| 用户 | 必须完成的任务 |
| --- | --- |
| 教师 | 创建/编辑题目，设置题目说明和名额，查看申请并确认或调整结果 |
| 学生 | 浏览和筛选题目，查看剩余名额，填报志愿，查看处理结果 |
| 项目负责人 | 维护基础数据、查看关键流程是否可用；第一版不单独设计复杂管理员后台 |

### 第一版必须具备

1. 教师可维护题目名称、简介、标签、要求与名额。
2. 学生可按关键词或标签浏览题目，并查看题目状态。
3. 学生可提交有限数量的志愿；系统提示重复提交和无效数据。
4. 教师可查看某个题目的申请列表，确认、拒绝或调整申请。
5. 学生可查看自己的最终状态；公开页展示题目的选题进度，不公开个人敏感信息。

### 第一版明确不做

- 移动端原生 App、应用商店上架和支付；
- 即时聊天、社交动态、完整课程/教务管理；
- 未经教师确认的自动录取或“AI 决定谁被录取”；
- 接入真实学生数据前的生产级权限体系。

## 5. NABCD 草案

### N — Need（需求）

课程选题常通过 Excel、表单和群消息协作。学生难判断题目状态，教师需要手工汇总和回复，且在名额、重复申请与处理结果上容易产生沟通成本。

### A — Approach（方案）

做一个轻量 Web 应用，集中展示题目、名额和要求；学生提交志愿；教师在一个界面处理申请；系统提供明确的状态与校验提示。

### B — Benefit（收益）

- 学生：少在群里反复询问，能随时查看题目和自己的进度。
- 教师：减少手工整理、重复答疑和遗漏申请的风险。
- 课程小组：有完整的需求、原型、代码、测试和反馈过程可供验收。

### C — Competitors / Alternatives（替代方案）

当前替代方案通常是 Excel、问卷表单、在线文档或群聊。它们适合收集信息，但题目状态、名额校验、审批流程和结果查询需要人工维护。CourseMatch 的差异是把这些步骤放入一个可追踪流程中。

### D — Delivery（交付）

第一版交付一个可公开访问的 Web 演示：教师创建题目，学生提交志愿，教师处理申请，学生查看结果。配套提交需求文档、原型、测试证据、用户反馈与 Gitee 过程记录。
