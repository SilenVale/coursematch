# CourseMatch 团队共同基准（组员阅读版）

> 这是一份共同起点：用于理解当前产品做什么、核心流程怎样运行，以及个人分析可以从哪里提出改进。它不是让大家重复写的长需求文档。

## 1. 我们要做什么

CourseMatch 是一个帮助教师组织课程选题的 Web 系统。

它要解决的不是“展示题目”本身，而是：**多人竞争有限名额时，怎样让规则公开、过程可复核、结果可解释。**

## 2. 一张图看懂主流程

打开 [团队共同业务基线图](./assets/team-baseline-workflow-v2.html) 查看可交互版本。

```text
教师创建活动：名单、题目、名额、资格条件、截止时间
        ↓
公开规则并开放填报
        ↓
学生浏览题目，提交 1～3 个不重复、有顺序的志愿
        ↓
截止：系统冻结全部数据，并为每位学生固定随机序号
        ↓
第 1 轮统一处理全体第一志愿
同题同轮超额 → 按随机序号从小到大分配
        ↓
仍未分配的人再处理第二、第三志愿
        ↓
学生查看个人结果与原因；失败者进入补选
```

## 3. 已经确定、不需要重复讨论的规则

1. 每名学生最终最多分配一个题目；每个题目的名额由教师设置。
2. 第一志愿一定先于任何人的第二、第三志愿处理。
3. 随机序号只用于“同一题目、同一轮次”的超额竞争；截止后生成且不可重抽。
4. 主分配只能执行一次，不能因为不满意而重新运行。
5. 未分配学生只可从剩余名额中补选；不强制分配不愿意的题目。
6. 教师可处理退选、题目取消、资格信息错误等异常，但必须说明原因并留下记录。

## 5. 每个人可以发挥的地方

请从自己的模块出发，思考下面三件事：

- 这个用户在什么情况下要完成什么事？系统应怎样判断并反馈？
- 哪些边界情况最容易让用户不理解或让结果不公平？
- 有什么具体功能能让“公平、公开、可解释”做得更好？

可以大胆提出想法，但要说明用户什么时候用、页面怎样展示、需要什么数据、怎样测试。创意在团队评审通过前只是候选，不能自行改动第 3 节的共同规则。

每位成员应回答与自己模块对应的具体问题，见 [模块评审问题单](./MODULE_REVIEW_QUESTIONS.md)。

## 6. 当前边界

第一版不做项目组管理、学生互换题目、AI 决定录取、支付、聊天、完整教务系统或原生 App。

老师已确认：**HTML 可交互 Demo 可以代替墨刀原型**；低保真图和页面状态图作为补充材料。
