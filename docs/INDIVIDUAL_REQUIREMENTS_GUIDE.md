# CourseMatch 个人需求分析写作说明

## 1. 唯一项目基线

全组以 [正式需求分析文档](./REQUIREMENTS_ANALYSIS.md) 为唯一项目需求基线。每个人的个人报告必须与该文档保持一致，尤其不得改写以下已经确认的规则：

- 每名学生最终最多分配一个题目；教师为题目设置可容纳学生人数；
- 学生可填写 1 至 3 个不重复的有序志愿；
- 截止后冻结数据和随机序号；
- 先处理所有学生的第一志愿，再处理未分配学生的下一志愿；同题同轮超额时按冻结随机序号决定；
- 主分配只执行一次；未分配学生参与补选，异常调整必须留痕。

基线保证团队项目只有一套产品定义；个人报告用于说明每位成员对负责模块的理解、建议和验收思路。

## 2. 每人提交内容

每位成员在共享基线之外，单独完成 1 至 2 页个人需求分析。建议按以下结构撰写：

1. **负责模块与目标**：说明本人负责什么，以及该模块为哪个角色解决什么问题。
2. **对应需求**：引用基线中的相关功能需求编号（如 `FR-01`），转写为本模块可实现的页面、字段、状态或接口需求。
3. **个人建议**：提出 2 至 3 条明确建议或风险；若建议改变基线，必须标注“待团队确认”，不能擅自当作既定规则。
4. **关键边界 / 异常**：列出至少 2 个需要处理的异常或限制。
5. **验收方式**：给出至少 2 个可验证的通过条件。

不要复制整份基线后仅替换姓名；也不要写出与基线冲突的新分配算法。

## 3. 按成员分配的写作重点

| 成员 | 负责模块 | 建议重点 |
|---|---|---|
| 汪奕辰 | 产品、完整可点击原型 / 静态页面、进度与验收 | 需求范围取舍、教师端与学生端关键流程、原型如何覆盖核心状态、整体验收 |
| 石俊贤 | 教师端、数据模型、分配逻辑、接口与数据库 | 活动 / 题目 / 名额配置、冻结快照、分配幂等性、调整记录与数据约束 |
| 刘家铭 | 学生端、表单交互、志愿排序、结果展示与接口联调 | 浏览与筛选、志愿排序与校验、截止后的只读状态、结果解释与补选交互 |
| 罗子超 | 测试、缺陷记录、用户试测与发布验收 | 主流程测试、名额 / 重复志愿 / 截止 / 同轮冲突等边界用例、缺陷分级与验收证据 |

## 4. 提交前检查

- [ ] 已明确引用 `REQUIREMENTS_ANALYSIS.md` 作为项目基线；
- [ ] 已写清个人负责模块，而不是只描述整个系统；
- [ ] 个人建议与基线不矛盾，或已明确标记为待团队确认；
- [ ] 已写出异常场景与可验证的验收条件；
- [ ] 文件名包含成员姓名或 GitHub 用户名，便于个人平台提交和仓库归档。
