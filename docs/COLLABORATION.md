# CourseMatch 团队协作规则

## 工具分工

| 工具 | 用途 | 不承担的用途 |
| --- | --- | --- |
| 微信群或线下会议 | 快速沟通、卡点、会议通知、PR 链接 | 不记录最终任务状态或代码版本 |
| GitHub Issues | 任务、负责人、验收条件和优先级 | 不替代课程文档 |
| GitHub 分支和 Pull Request | 代码变更、审查和合并历史 | 不作为闲聊渠道 |
| GitHub `docs/` 与[证据索引](EVIDENCE_INDEX.md) | 立项、原型、进度、测试和用户反馈的课程证据 | 不以历史 Wiki 的存在替代可复核原始材料 |
| `master` 分支 | 当前可运行、可演示的团队版本 | 不作为个人试验区 |

## 成员权限

- 仓库所有者：维护成员、分支规则、Issue、Wiki 与最终合并。
- 组员：使用“开发者”权限，创建分支、提交代码和 Pull Request。
- 除仓库所有者外，不授予管理员权限。

## 每项开发任务的固定流程

```text
GitHub Issue 写清任务和验收条件
        ↓
从最新 master 创建任务分支
        ↓
开发、手动验证、检查 diff
        ↓
提交并推送分支
        ↓
创建 Pull Request，说明改动和验证结果
        ↓
审查通过后合并到 master
        ↓
Issue 标记完成，下一项任务从更新后的 master 开始
```

## 分支和提交命名

- 功能：`feat/issue-12-topic-list`
- 修复：`fix/issue-18-duplicate-selection`
- 文档：`docs/issue-3-project-initiation`
- 提交：`feat: 增加题目筛选`、`fix: 修复重复申请校验`、`docs: 更新选题思维导图`

每个分支只解决一个 Issue。若发现工作范围已经改变，先新建或拆分 Issue，不把无关功能塞进同一 Pull Request。

## 合并规则

1. 禁止直接向 `master` 推送，禁止 `force push`。
2. Pull Request 必须说明：关联 Issue、实现内容、已验证项、未验证项和已知风险。
3. 至少由一位非提交者检查范围和验收条件；第一阶段可由仓库所有者完成。
4. 有冲突时先停止合并，确认两边的业务意图后再解决；不让 AI 在不理解业务的情况下二选一。
5. 合并后由负责人确认 `master` 能正常启动或至少不破坏已有流程。

## 第一周的协作方式

第一周尚未进入编码。组内按以下方式留痕：

- 会议负责人：记录参会者、时间、结论并拍摄会议照片；
- 产品材料负责人：产出头脑风暴思维导图和 NABCD；
- 仓库负责人：将课程核验材料整理到 GitHub 仓库；早期 Gitee Wiki 留作历史记录；
- 全员：确认选题、项目边界和本人后续角色。

会议照片、成员身份和实际讨论结论必须来自真实会议，不能后补或虚构。
