# CourseMatch 模块需求分析与创意提案任务书

## 1. 目的与提交方式

本任务书用于把团队共同的需求基线，转化为每位成员可负责、可评审、可实现、可测试的模块分析。每个人应在自己的分支创建一份个人文档，文件建议命名为：

```text
docs/personal/<姓名或GitHub用户名>-模块需求分析.md
```

个人文档不是重复整份项目需求，而是基于共同规则完成“我的模块怎样实现、怎样验证、还能怎样做得更好”的分析。完成后通过 Pull Request 提交，由负责人汇总。

## 2. 不可自行改变的共同基线

所有个人分析必须以 [正式需求分析文档](./REQUIREMENTS_ANALYSIS.md) 为准。以下规则已冻结；个人建议不能直接改写它们：

1. 每名学生最终最多分配一个题目；教师设置每个题目的可容纳学生人数。
2. 学生可提交 1 至 3 个不重复、有序志愿；截止前最后一次有效提交为准。
3. 截止后冻结参与名单、题目、名额、资格条件、志愿和每位学生唯一随机序号。
4. 第 1 轮处理全体第一志愿；第 2、3 轮只处理仍未分配学生的下一志愿。
5. 同题、同轮超额时，按冻结随机序号升序分配；主分配只执行一次，不允许重抽。
6. 所有志愿均失败的学生进入补选；补选只竞争剩余名额，继续沿用冻结随机序号。
7. 教师只可处理退选、题目取消、资格信息错误、公开硬性条件不匹配等预定义异常，且必须留下记录。

当前 HTML 可交互 Demo 已获老师确认，可替代墨刀原型；低保真图和页面状态图作为原型补充材料。

## 3. 每份个人文档必须回答的六件事

### 3.1 模块目标

说明你负责的用户是谁、在什么活动状态下完成什么任务，以及成功后得到什么结果。

### 3.2 具体业务逻辑

按“输入 → 校验 / 判断 → 系统处理 → 页面反馈”描述模块内的关键动作。不要只写“实现列表、按钮、接口”。

### 3.3 页面与状态

列出本模块涉及的页面或页面区块，并说明至少一个正常状态、一个空状态、一个异常 / 禁用状态。

### 3.4 数据与接口边界

列出本模块最关键的数据字段、前端需要调用什么、后端必须保证什么。前端不得自行计算分配结果或修改冻结数据。

### 3.5 异常与验收

至少列出 3 个边界场景，以及对应的可验证通过条件。

### 3.6 创意提案

提出 2 至 3 个可选创意；每个都必须使用第 5 节的提案卡，不能只写“增加 AI”“优化体验”之类的口号。

## 5. 创意提案卡（每项创意都按此格式写）

```markdown
### 创意名称

- 解决的具体问题：
- 受益用户：教师 / 学生 / 两者
- 用户在什么时刻使用：
- 交互或页面表现：
- 需要的数据与关键判断：
- 与共同基线的关系：不改变基线 / 需要团队决议后才改变
- 如何在 HTML Demo 中展示：
- 如何测试是否有效：
- 实现成本：低 / 中 / 高；原因：
- 风险或隐私影响：
```

推荐优先探索的方向是“**可解释公平分配**”，而不是让 AI 决定谁被录取。例如：

- 学生个人结果解释卡：展示命中志愿、处理轮次、竞争人数、名额、随机序号和结果原因；
- 去隐私化的分配过程回放：按轮次展示题目候选人数、分配人数和剩余名额，不公开他人的具体志愿；
- 填报期志愿风险提示：根据当前汇总热度与名额提示“竞争较高”，但不预测录取、不替学生做决定；
- 教师规则发布检查：开放活动前以清单提示是否已配置名单、题目、名额、截止时间和规则。

## 6. 创意筛选规则

团队汇总创意时，每项按以下五项各评估“是 / 否”：

1. 是否直接改善“公平、公开、可解释”的选题核心问题？
2. 是否可以在 HTML Demo 中清晰演示，而不只是写在文档里？
3. 是否可以在当前课程周期内完成，并有明确责任人？
4. 是否能写出清晰的测试用例和验收条件？
5. 是否不破坏共同基线中的冻结、轮次优先、随机序号和名额约束？

只有五项均为“是”的创意，才进入候选池。团队最终选择 **1 个主创新点** 和至多 **2 个辅助亮点**；通过后更新需求基线、HTML Demo、概要设计和测试用例，确保所有材料一致。

## 7. 必须形成的设计追踪链

每个模块至少选 3 条需求，形成如下链路：

| 需求编号 / 业务规则 | 原型页面或状态 | 概要设计对象 | 详细设计内容 | 测试用例 |
|---|---|---|---|---|
| 示例：FR-04 志愿维护 | 学生填报页：编辑中 / 校验失败 / 已提交 | PreferenceSubmission、学生端服务 | 志愿去重、最多 3 个、连续排序校验 | 重复题目、超过上限、截止后编辑 |

这条链路直接对应课程评分中的需求分析、原型系统设计、概要设计、详细设计与测试，后续报告不需要重新猜测材料之间的关系。

- [ ] 已写出具体输入、判断、结果和页面状态；
- [ ] 至少有 3 个异常 / 边界场景和可验证的验收条件；
- [ ] 每个创意都有提案卡、Demo 展示方式和测试方式；
- [ ] 个人文档与现有 HTML Demo、需求基线不矛盾；
- [ ] 已通过独立分支和 Pull Request 提交。
